# МКР №1. Як я покращив планування покупок за допомогою AI

## Задача та план

Мій проєкт — **«Смак & Кошик»**: локальний вебзастосунок, який приймає довільно скопійовані рецепти, складає спільний список продуктів за відділами магазину та знаходить відповідні товари в АТБ і «Сільпо» у Житомирі. Додатково є чат про поточні рецепти та звичайний чат.

| Поле | Рішення |
| --- | --- |
| Проблема | Для кількох страв доводиться вручну переносити інгредієнти, зберігати діапазони, об’єднувати повтори та шукати ціни в різних магазинах. |
| Поточний процес | Прочитати рецепти → виписати продукти → звести повтори й одиниці → відняти наявне → знайти ціни й фасування. |
| Реальні дані | Користувач надав рецепти борщу, тушкованої капусти та піци. Тексти з емодзі, кроками й підписами фото збережено у `evidence/usage/`. |
| Рівень рішення | **2 — LLM + tools.** Модель розуміє довільний текст і веде діалог; окремі інструменти отримують ціни й виконують арифметику. |
| Ціль якості | Знайти щонайменше 95% явно названих основних інгредієнтів на перевірених випадках, не видавати вигадані кількості за дані рецепта. |
| Ціль часу | Скоротити час підготовки та перевірки спільного списку щонайменше удвічі на однаковому завданні. Для списку без цін: 172 с → не більше 86 с; для повного процесу: 432 с → не більше 216 с. |
| Fallback | Редагування, цитати, вибір іншого товару, явне «не знайдено», позначений кеш і ручне додавання підтвердженої ціни. |

Початковий план до реалізації збережено у `evidence/plan_before.md`. Сортування за категоріями й приблизні ваги додано після зворотного зв’язку користувача.

## Як працює рішення

| Компонент | Призначення |
| --- | --- |
| Браузерний інтерфейс | Вставлення рецептів без форматування, редагування, категорії, порції, вибір товарів, історія та два чати. |
| Qwen3.5 4B через Ollama | Виділення інгредієнтів зі структурованим JSON і точними цитатами, відповіді в чатах. Для продуктів лише з подачі є додаткова перевірка відповідних фраз. |
| Qwen3.5 9B через Ollama | Окремі приблизні пропозиції маси/об’єму для штук, ложок і невідомих кількостей. Оцінки для попереднього кошторису відокремлені від вихідного рецепта; явне прийняття потрібне лише для заміни робочої кількості. |
| Python | Перевірка чисел і цитат, відновлення явно записаних одиниць, об’єднання сумісних величин, категорії та кількість упаковок. |
| Адаптер АТБ | Звичайна анонімна сесія, вибір магазину Житомира та читання HTML-каталогу. Без оформлення кошика чи замовлення. |
| Адаптер «Сільпо» | Публічний JSON-каталог конкретного відділення, назва, базова ціна, фасування й залишок. |
| SQLite та JSONL | Локальна історія списків і докази фактичних запусків. Кеш і робоча база виключені з Git. |

Ціни не генерує мовна модель. Для вагових товарів береться ціна за кг, а не значення за 100 г. Для фасованих товарів потрібна ціла кількість упаковок. Штуки не змінюються в оригінальному списку. Для **попереднього кошторису** окремо використовується приблизна AI-вага, а для невизначених продуктів комори — одна упаковка з явною позначкою. Відомі 1200 г капусти сервер додає до оцінки лише невідомої частини. Оригінальний запис залишається видимим.

Обрані магазини: АТБ — **вул. Велика Бердичівська, 70б**, «Сільпо» — **вул. Грушевського Михайла, 5**. Ціни інших адрес не видаються за ціни цих магазинів. Умовні знижки за карткою АТБ і доставка не включаються.

## Перевірка на реальних рецептах

| Рецепт | Основні продукти | Для подачі | Розбір, с |
| --- | --- | --- | --- |
| Борщ | 11/11 | 3/3 | 11.11 |
| Тушкована капуста | 9/9 | 1/1 | 7.59 |
| Піца | 11/11 | 0/0 | 7.72 |

У перевірених випадках знайдено **31/31 основних інгредієнтів** та **4/4 додаткових продуктів для подачі**. Це перевірка назв за вручну складеним переліком понять, а не доказ безпомилкової роботи на будь-яких рецептах. Датасет малий і був використаний під час розробки, незалежного широкого тесту немає.

Окремо перевірено:

- «5 л каструля» не стає продуктом; кроки, час і підписи фотографій не додаються до списку.
- «5–10 шт. ребер» зберігається діапазоном; довільна маса не приписується оригіналу.
- Капуста з відомими 1200 г і додатковою невідомою кількістю не перетворюється на повністю відому суму.
- У паприці збережено 1 ч.л. загалом: дві згадки по 0.5 ч.л. описують використання цієї кількості.
- Повтор «200 г моцарели» враховується один раз і позначається для уточнення; 400 г автоматично не оголошуються правильними.
- Цибуля різного опису об’єднується, але штуки та грами одного продукту не складаються без додаткових даних.
- Продукти для подачі спочатку виключені з покупок, їх можна ввімкнути.

Фактичні відповіді: `evidence/technical/extract_*.json`, перевірки — `extraction_summary.json`, `reference_inventory.json`. Детерміновані тести перевіряють одиниці, повтори, категорії, упаковки, залишки та відхилення нерелевантних готових страв.

## Перевірка каталогів і відсутніх товарів

| Магазин | Знайдено кандидатів | Перевірено інгредієнтів |
| --- | --- | --- |
| ATB | 21 | 25 |
| Сільпо | 24 | 25 |

Це **покриття пошуку кандидатів**, а не гарантія, що кожен товар — ідеальна заміна інгредієнта. Вид, обробку, фасування й бренд потрібно звіряти. Через «Змінити товар» доступні альтернативи та ручне внесення перевірених даних.

На момент перевірки свинячі ребра в обраному каталозі АТБ не знайдені. Це відображається як **«Не знайдено»**, без автоматичної заміни іншим м’ясом і без нульової ціни. Якщо відповідні товари є, але всі мають нульовий залишок, статус — **«Немає в наявності»**. Якщо недоступний сам каталог — окрема помилка або явно позначений старий кеш.

Неповні кошториси мають число порахованих продуктів. Порівнювати їх як повні однакові кошики й оголошувати дешевший магазин не можна. Живі відповіді, посилання, адреси й час збережено у `all_prices.json` та `two_recipe_prices.json`.

## Результати до / після

Користувач реально виміряв час для **борщу й тушкованої капусти**, без піци:

| Операція | До AI |
| --- | ---: |
| Складання спільного списку | 172 с — 2 хв 52 с |
| Пошук цін АТБ | 120 с — 2 хв |
| Пошук цін «Сільпо» | 140 с — 2 хв 20 с |
| Разом | 432 с — 7 хв 12 с |

Для того самого двохрецептного входу технічний запуск прототипу дав:

| Показник | Виміряний результат |
| --- | ---: |
| Виділення та об’єднання модельних даних | 18.62 с |
| Свіжий пошук у двох каталогах разом | 5.60 с |
| Разом ці технічні етапи | 24.22 с |
| Оцінка результату людиною | Користувач перевірив першу спробу й повідомив про недоліки |
| Повний час після для списку без цін | Поки не зафіксований |
| Повний час після з двома магазинами та перевіркою | 52 с — перша спроба з зауваженнями |
| Оплата API одного прогону | 0 грн — локальні моделі; без платного API |

Перша реальна спроба користувача тривала 52 с проти 432 с вручну (на 88.0% менше), але користувач оцінив ціни й кількості як недостатньо зручні. Це не видається за підсумковий успіх. Після цього кошторис перероблено; окремого повторного заміру користувача для нової версії немає.

Електроенергію, амортизацію обладнання й час первинного встановлення окремо не виміряно. Тому «0 грн API» не означає нульову загальну собівартість. Пошук двох магазинів виконується частково паралельно, тому його час не ділиться довільно навпіл. Додаткові AI-оцінки кількостей — окремий запит і не приховані в початковому часі розбору.

## Доопрацювання після реального використання

Користувач зберіг список після 52-секундної спроби та вказав, що майже всюди потрібні уточнення. У першій версії ціни були знайдені для 12/15 позицій АТБ та 14/15 «Сільпо», але зіставлення штук/ложок із грамами блокувало більшість сум. Діапазони також надмірно позначалися як проблеми.

Після зворотного зв’язку:

- звичайний діапазон із рецепта став нейтральною позначкою;
- для попереднього кошика автоматично пропонується вага, без зміни оригіналу;
- невизначені спеції та соуси попередньо рахуються як одна упаковка;
- свіжі ребра «Сільпо» по 254 грн/кг випереджають дорожчі заморожені;
- непідтверджені точні товари залишаються пропусками, а не підміняються схожими;
- збережено вихід першої спроби в `evidence/usage/first_user_session.json`, щоб не приховувати недоліки.

| Магазин | Пораховано / знайдено | Попередня сума, грн | Не знайдені точні товари |
| --- | --- | --- | --- |
| АТБ | 12 / 12 | 216.97 | куряче стегно без кістки та шкіри, ребра свинячі, мелений духмяний перець |
| Сільпо | 14 / 14 | 1119.00 | мелений духмяний перець |

Суми непорівнянні як однакові повні кошики: в АТБ немає підтвердження обох потрібних м’ясних позицій. Це попередній бюджет за верхніми межами вагових оцінок і цілими упаковками, без доставки.

Актуальний кошторис і покриття після доопрацювання зберігаються окремо в `evidence/technical/improved_basket_summary.json`. Це технічна перевірка другої версії, а не нове вимірювання часу користувача.

## Відповіді на 12 запитань

1. **Яку проблему вирішено?** Перенесення продуктів із довільних рецептів у спільний список та первинний пошук цін у двох магазинах.
2. **Чому проблема реальна?** Користувач надав свої рецепти й фактичні вимірювання ручного складання списку та пошуку цін. Вхід не вигадано спеціально як простий синтетичний приклад.
3. **Як робилося до AI?** Ручне читання, таблиця, об’єднання повторів і окремий пошук кожного продукту в АТБ та «Сільпо».
4. **Яке рішення побудовано?** Локальний вебзастосунок зі структурованим розбором, категоріями, редагуванням, приблизними вагами, каталогами, чатами й історією.
5. **Чому рівень 2?** Одного промпту недостатньо для актуальних цін; потрібні зовнішні інструменти. Сценарій заданий програмою, автономний агент і донавчання не потрібні.
6. **Які альтернативи?** Звичайний чат без парсера, регулярні вирази, ручна таблиця, RAG і fine-tuning. Регулярні вирази використано для перевірки явних чисел, але вони самі не розуміють довільні кроки й альтернативи. RAG не потрібен для трьох безпосередньо наданих текстів і не замінює живий каталог.
7. **Які моделі та інструменти?** Qwen3.5 4B і 9B через Ollama; Python, requests, BeautifulSoup, SQLite; HTML/CSS/JavaScript. Запуск перевірено на Windows із RTX 5070.
8. **Які помилки виникли?** Пропуск подачі, зайві слова в пошуку, нерелевантні готові страви, втрата одиниць та невдалі припущення маси. Конкретні виправлення й обмеження наведені вище; журнал розробки збережено.
9. **Наскільки надійне рішення?** Придатне для чернетки списку з перевіркою людиною. Джерельні кількості, арифметика й отримані ціни відокремлені від приблизних порад моделі. Повністю автономні покупки не виконуються.
10. **Що змінилося?** З’явився один список за відділами, автоматичне об’єднання сумісних величин, цитати, позначення проблемних рядків та порівняння підтверджених товарів.
11. **Скільки вдалося заощадити?** Відомий ручний час — 432 с із пошуком двох магазинів; технічні етапи прототипу — 24.22 с. Економія всього процесу обчислюється лише за повним вимірюванням користувача, а не за часом генерації. Перша реальна спроба користувача тривала 52 с проти 432 с вручну (на 88.0% менше), але користувач оцінив ціни й кількості як недостатньо зручні. Це не видається за підсумковий успіх. Після цього кошторис перероблено; окремого повторного заміру користувача для нової версії немає.
12. **Що розвивати далі?** Більше незалежних реальних випадків, кращий вибір магазинів, точніший пошук товарів за властивостями, оцінка витрат на фактичній покупці й персональний список наявних продуктів.
